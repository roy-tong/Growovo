# 实施路线、优先级与验收

> 原则：先修事实与对象，再跑通一条工作，再扩岗位和行业。不要先新增 40 个 Agent、更多平台文案或自动生成器。
>
> 当前进度：R0 与 R1 已有本地实现和测试，详见 [05-implementation.md](05-implementation.md)；R2 起仍是后续工作，不能按文档完成度冒充产品完成度。

## 1. 优先级不是岗位价值排名

排序依据：共享复用度、业务发生频次、结果可核验性、现有代码基础、数据接入成本和风险。P3 表示应做独立行业包，不表示业务价值低；如果某行业就是目标客户，对应包应提升到 P1。

| 层级 | 范围 | 原因 |
|---|---|---|
| **P0 共享与纠错** | 上下文、WorkOrder、SOP、Deliverable、Handoff、Metric、Permission；41 / 42 / 43 / 44；45 只做只读与沙盒 | 没有共同对象和口径，所有岗位只能生成动作量报表 |
| **P1 默认可验证闭环** | 09 / 10 / 11 / 12 / 14 / 18 / 24 / 25 / 26 / 27 / 28 / 35 / 38 / 40 / 46 | 能串起内容、需求、销售、激活、留存与开发者真实使用，结果源相对明确 |
| **P2 规模化触达与关系扩展** | 07 / 08 / 13 / 15 / 16 / 17 / 19 / 20 / 21 / 34 / 36 / 37 / 39 | 复用 P0 / P1 资产与结果连接；付费、激励和公开传播先建停止与反作弊 |
| **P3 独立行业包** | 22 / 23 / 29 / 30 / 31 / 32 / 33 | App、跨境、电商、直播、供给、渠道和线下对象 / 法规差异大，应独立适配 |

**行业提升规则**：App 客户把 22 提升；跨境客户把 23 提升；电商客户把 29 / 31 提升，直播为核心再提升 30；渠道 / 线下为核心提升 32 / 33；开发者产品把 46 提升；本地口碑业务把 15 提升。

## 2. 发布切片

### R0 · 修正当前事实与边界

**目标**：在加新对象前，消除现有实现中会产生错误业务判断的逻辑。

范围：

1. Conversion 的全阶段证据、资格、初始阶段与报价前置条件；
2. cohort 漏斗算法，当前阶段存量改名且不再冒充转化；
3. deals 事件追加 + 当前投影，或统一实现 / 文档语义；
4. 移除 execute 的无真实依据 `evidence_grade="B"`；
5. result 接入 TaskOutcome，三层结果同源；
6. FinOps 销售内容迁移为垂直 Overlay；
7. WorkOrder / Subject / Deliverable / Outcome 关联 ID 方案与迁移规范。

**完成判据**：R0 测试全部通过；非 FinOps fixture 不出现发票、固定报价或七文件交付；committed 仍不能推导 task / business outcome。

### R1 · 共享业务内核（第一条垂直切片）

**目标**：不用外部平台，也能从工作目标跑到交付验收和交接。

实现：

- Capability Registry：18 能力域、40 岗位族及完整性 lint；
- BusinessContextSnapshot、Objective、Workstream、WorkOrder；
- SOPVersion / StepRun / DoD / 异常；
- TemplateVersion / DeliverableVersion / AcceptanceReview；
- Handoff / SLA / 拒收返工；
- MetricDefinition / Measurement；
- 最小 RBAC 与职责分离；
- ActionRequest 适配现有 plan / queue，不新增 transport 旁路。

**第一条 fixture**：内容运营 09 → 文案 10 → 社媒 12 → 产品激活 24 → 数据 44。

**完成判据**：缺事实包时内容任务 blocked；文案未验收时社媒不能发布；社媒回执只更新执行层；激活事件必须有独立产品来源；每个对象可从结果反查任务。

### R2 · 两条可核验业务主链

#### R2A · B2B 需求到客户成功

```text
09/10 内容 → 18 Demand/ABM → 26 SDR → 27 AE
→ 28 POC → 27 合同/回款 → 38 CSM → 40 支持 → 43 RevOps
```

必做：账户 / 购买组、SAL 接收、机会阶段证据、POC 章程、成交交接、成功计划、回款 / 续约来源、销售拒收回流。

#### R2B · PLG / 开发者到持续使用

```text
09/14/46 内容与文档 → 24 激活 → 25 CRO
→ 35 Lifecycle → 34 留存 → 38 客户成功（如适用）→ 44 数据实验
```

必做：合格主体、价值事件、首次成功、队列留存、频控 / DNC、版本化 onboarding 和真实示例复现。

**完成判据**：两条链均至少有本地端到端 fixture 和一次真实 dogfood 业务验收；外部动作另按渠道验证，不用 fixture 冒充真实效果。

### R3 · 触达、合作与自动化扩展

- 07 / 08 / 13 / 15 / 16 / 17 / 19 / 20 / 21 / 34 / 36 / 37 / 39；
- 45 从只读 / 沙盒扩到有限生产自动化；
- 预算、反作弊、权利、危机、频控和客户授权先于自动优化；
- 自动扩量始终需要人审，异常默认停而非自动追加预算或频率。

### R4 · 行业包

按目标客户选择，不追求同时上线：

- App Pack：22 + 14 / 17 / 24 / 35；
- Regional Pack：23 + 本地法务 / 语言 / 支付 / 支持；
- Commerce Pack：29 / 31 + 17 / 35 / 40；
- Live Pack：30 + 29 / 31 / 40；
- Partner / Local Pack：32 / 33 + 20 / 27 / 42；
- Developer Pack：46 + 09 / 12 / 24 / 40（若未在 R2 提前）。

每包必须有独立对象、模板、指标、权限、 fixture 和真实业务验收，不能只换文案。

## 3. 三条灯塔 dogfood

### D1 · 开发者内容与激活

- **岗位**：09 / 10 / 46 / 12 / 24 / 44；
- **真实工作**：从已确认产品事实生产一个可运行教程，发布到授权渠道，处理开发者问题，观察首次成功运行；
- **核心交付**：教程 brief、可运行 repo / 示例、发布包、互动记录、激活事件定义与复盘；
- **业务验收**：技术 Owner 复现通过，渠道 Owner 接受发布包，至少一个外部开发者结果有独立证据；没有则如实记录未观察；
- **禁止**：用 Star、页面浏览或发帖回执代替首次成功。

### D2 · B2B 商机的完整交接

- **岗位**：18 / 26 / 27 / 28 / 38 / 42 / 43；
- **真实工作**：一个目标账户从触发到 SAL、机会、POC / 商务，再到客户成功；
- **核心交付**：账户计划、资格卡、MAP、POC 章程、成交交接、成功计划与指标字典；
- **业务验收**：每一接收角色签收；如果停在早期阶段，也以“停在何处、缺什么”验收，不伪造合同 / 回款；
- **禁止**：用会议、报价或 POC 完成代替付款，用销售金额代替净收入。

### D3 · 留存风险与服务恢复

- **岗位**：34 / 35 / 38 / 40 / 44；
- **真实工作**：从一个真实使用 / 服务风险到解决确认和持续使用观察；
- **核心交付**：风险卡、Journey、服务恢复记录、客户确认、留存观察与规则 diff；
- **业务验收**：用户或行为证据确认问题解决；后续窗口未成熟就显示未成熟；
- **禁止**：发送召回消息或关闭工单即宣布挽回。

## 5. 场景分支与风险控制

### 5.1 低频项目制

07 品牌重塑 / 大 campaign、08 危机、19 大型活动、23 区域上线、32 伙伴谈判、37 忠诚体系重设计、39 案例 / 顾问会采用项目里程碑、预算、风险登记与阶段签批；不能套日更内容或 SDR 的产量 SLA。

### 5.2 高风险硬门禁

- 公共主张 / 版权 / 客户授权：07 / 08 / 10 / 11 / 12 / 13 / 15 / 30 / 39；
- 花费 / 合同 / 价促 / 佣金：17 / 20 / 21 / 27 / 29 / 32 / 37 / 42；
- 联系人 / 同意 / 敏感数据：18 / 23 / 26 / 34 / 35 / 36 / 40 / 41 / 45；
- 生产写入：24 / 25 / 41 / 45；
- POC / 示例安全：28 / 46。

系统可草拟、校验和推荐，不得自动越过这些门禁。刷评、隐瞒商业合作、伪造倡导、无证据公共主张和暗黑模式是禁止动作，不是“可优化护栏”。

### 5.3 低流量 / 长周期

样本不足时可采用可用性测试、分阶段发布、访谈（交 Askovo 深研）或明确标注的观察性前后对比；不得称为已验证实验提升。品牌、公关和倡导可用 sourced / influenced 和适当对照，不强套 last-click。

## 6. 研发完成定义（Definition of Done）

每项产品功能只有同时满足以下条件才可标“本地可用”：

1. Schema / lint、状态机、权限和事件审计实现；
2. 正向、失败、未知、越权、返工、版本变化与回滚测试；
3. CLI / MCP / Skill 入口语义一致，没有审批旁路；
4. 用户文档说明输入、步骤、交付物、限制与验证等级；
5. 相关既有测试无回归：`python3 -m unittest discover -s tests` 与 `python3 mkt.py demo`；
6. 不使用真实账号发送做 CI；
7. 业务验收另行记录，不能由测试通过自动升级。

“外部验证可用”还需授权真实账号 / 数据、目标平台回读和业务 Owner 验收；“业务有效”需独立结果证据；“增量有效”需符合设计的实验 / 准实验。这三者不得写在同一个布尔值里。

- 已把 40 个岗位全部实现为可运行代码；
- 已完成所有外部平台实时规则研究或账号验证；
