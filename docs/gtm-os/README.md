## 0. 一页结论

Growovo 不应被设计成“46 个岗位 Agent”，也不应继续以“选目标—选渠道—发内容”为产品总流程。它应成为一套 **以工作委托单为载体、以专业 SOP 为方法、以合格交付物为最小完成单位、以真实业务结果为后验观察的 GTM 业务操作系统**。

### 0.1 八项核心决策

| # | 决策 | 直接纠正的问题 |
|---|---|---|
| 1 | **岗位是责任视角，不是 Agent 数量**。40 个岗位族归并为 18 个能力域，共用任务、交付物、审批、指标与证据内核 | 避免 40 套重复聊天机器人和不可维护的提示词 |
| 2 | **Work Order（工作委托单）是一等业务对象**，不是 campaign 的附属说明 | 让每项工作有目的、输入、负责人、SOP、交付物、验收、预算、期限和权限 |
| 3 | **完成一次动作不等于完成一项工作**。工作必须形成可验收交付物；外部发布只是某些 SOP 的一个步骤 | 解决“发了很多，但不知道做成了什么” |
| 4 | **SOP 是可执行步骤契约**。每步有输入、操作、工具、输出、DoD、证据、失败分支和责任人 | 解决“ playbook 只有平台知识和建议，没有专业过程” |
| 5 | **KPI 分结果、过程、护栏三层，指标必须带公式与数据来源** | 防止拿发布量、曝光量或主观评分冒充业务价值 |
| 6 | **跨岗位通过 Handoff 交接，靠接收方验收而不是发通知** | 解决内容给社媒、线索给销售、成交给客户成功时的信息断裂 |
| 7 | **模板同时约束内容、证据与验收**，不是只有标题的空白文档 | 让输出能直接审、直接执行、直接交接 |
| 8 | **复用现有授权执行内核**。业务层不能绕过 approval、pipeline、action_runner、ledger 和未知结果保护 | 保留 Growovo 已验证的安全优势 |

### 0.2 新的业务主链

```text
Askovo / 人工确认的业务上下文
  ↓
运营目标 Objective
  ↓
工作委托 Work Order
  ↓
专业 SOP Run（步骤、责任、异常、人审）
  ↓
交付物 Deliverable（模板、版本、质量验收）
  ↓
授权动作 Action（可选；仍走既有执行内核）
  ↓
跨岗位交接 Handoff（接收方验收）
  ↓
结果观察 Outcome（平台 / 任务 / 业务三层）
  ↓
复盘与规则修订（SOP、模板、指标口径均版本化）
```

渠道、Campaign、Queue、Workflow、日程和平台账号都仍然重要，但它们是这条主链使用的工具，不再替代业务工作本身。

## 1. 当前产品的真实基础与缺口

### 1.1 必须保留的基础

当前仓库已经提供以下可复用能力：

- `core/approval.py`、`core/planlint.py`：审批、版本指纹与执行约束；
- `core/pipeline.py`、`core/action_runner.py`、`core/queue_runner.py`：统一写路径；
- `core/ledger.py`、`core/task_outcome.py`：追加式回执、人工裁决和三层结果；
- `core/workflows.py`、`core/locators.py`：经审批的操作配方与语义恢复；
- `core/contacts.py`、`core/followups.py`：对象台账与跟进；
- `core/value_artifact.py`、`core/value_delivery.py`：价值资产和交付链；
- `core/journey.py`、`core/result.py`、`core/experiments.py`：旅程、结果和实验；
- `core/platforms.py`、`core/voice.py`、`core/playbook_model.py`：平台、语气与组合规则。

这些模块解决的是“如何安全地做、如何留下证据”。新设计补的是“为什么做、由谁做、按什么专业步骤做、交什么、谁验收、下一步交给谁”。

### 1.2 主要业务断点

| 当前状态 | 业务后果 | 本设计的修复 |
|---|---|---|
| goal / strategy / cadence / sprint 主要生成目标和排期 | 不能表达真实岗位职责与任务依赖 | Objective + Work Order + RACI + Dependency |
| playbook 以平台规则、动作列表和内容建议为主 | 缺少专业输入、步骤产物、DoD 和异常分支 | 版本化 SOP + Step Contract + Deliverable Spec |
| campaign 是主要组织单位 | 品牌、公关、售前、CS、RevOps 等工作无法自然落位 | Workstream / Work Order 为上位模型，campaign 只是一种执行编组 |
| 交付物没有统一版本、验收和接收方 | “生成文件”被误当成“工作完成” | Deliverable + Acceptance + Handoff |
| KPI 多为计数或漏斗投影 | 缺公式、分母、窗口、资格条件和护栏 | Metric Dictionary + Observation + Evidence |
| 销售流程包含特定 FinOps 案例和固定报价 | 被误用于所有 B2B 业务 | 通用销售骨架 + 行业 Overlay；案例移入示例包 |
| 跨角色协作主要靠用户自行理解 | MQL 被拒、POC 缺范围、成交后客户信息丢失 | 标准交接包与接收方签收 |
| 人工 / 机器二分 | 无法区分草拟、复核、承诺、付款、危机等权限 | 风险分级 + 步骤级 Actor + 审批矩阵 |

## 2. 产品范围与 Askovo / Verovo 边界

### 2.1 Growovo 接收什么

Growovo 开工前接收 `BusinessContext`。可以来自 Askovo，也可以由用户明确填写；后者必须标记为用户假设，不能伪装成已研究结论。

最小字段：

- 产品事实、适用场景、已有能力与明确不做什么；
- ICP / 受众、购买者、使用者、受益人及其来源；
- 已确认的价值主张、消息边界、可引用证据与禁用表述；
- 商业模式、已批准报价 / 折扣 / 促销边界；
- 目标市场、语言、区域、渠道资产与合规约束；
- 本轮运营目标、时间窗、资源、预算与责任人；
- 来源与版本：`source_ref`、`context_version`、`approved_by`。

缺少某项时，系统只阻塞依赖该项的工作。例如缺少已批准折扣边界，不妨碍写帮助中心草稿，但会阻塞促销发布和报价承诺。

### 2.2 不重复建设的上游能力

| 上游问题 | 责任方 | Growovo 的处理 |
|---|---|---|
| 卖给谁、为什么买、市场机会是否成立 | Askovo | 读取结论与依据，不自行宣布 ICP 已验证 |
| 产品定位、差异化、价值主张 | Askovo / 产品负责人 | 转成内容、销售和生命周期消息规范 |
| 市场进入战略与区域优先级 | Askovo / 业务负责人 | 把已选区域和渠道翻译为运营计划 |
| 定价与包装策略 | Askovo / 业务负责人 | 在批准的价格与折扣护栏内执行 |
| 成本核验与任务经济性 | Verovo | 读取成本和经济性结果，不用 Growovo 动作账本自证 ROI |

运营中产生的异议、流失原因、搜索词、客服问题和销售反馈可以形成“待研究信号”交回 Askovo，但 Growovo 不把这些便利样本直接升级成市场结论。

### 2.3 Growovo 自己负责什么

- 把已确认的业务上下文转成可执行的运营目标；
- 组织 07–46 岗位族对应的工作；
- 提供专业 SOP、方案模板、交付物和质量标准；
- 管理任务依赖、交接、审批、权限、日程和异常；
- 调用既有执行内核完成已授权动作；
- 记录结果指标、护栏指标和证据，推动版本化改进。

### 3.1 能力域不是行业模板的替代品

同一能力域采用“通用骨架 + 场景 Overlay”：

```text
基础 SOP（例如：客户续约）
  + 行业 Overlay（B2B SaaS / 消费订阅 / 硬件 / 电商）
  + 平台 Overlay（小红书 / LinkedIn / Shopify / 企业微信）
  + 企业 Overlay（审批、合规、品牌、数据、权限）
```

Overlay 只能增加或收紧约束，不能静默删除安全、证据和人审要求。小红书、TikTok、LinkedIn 运营共用受众—策划—生产—发布—互动—分析骨架，平台差异放在 Overlay 中，不复制三套业务内核。

## 4. 产品核心对象

| 对象 | 回答的问题 | 最小完成条件 |
|---|---|---|
| BusinessContext | 依据什么业务事实工作 | 有版本、来源、责任人与适用边界 |
| Objective | 这段时间要改变什么业务结果 | 有基线 / 未知声明、目标或学习问题、窗口、Owner、指标 |
| Capability | 这项专业工作应该怎么做 | 职责、KPI、SOP、模板、权限、交接完整 |
| Workstream | 一组工作如何共同服务目标 | 有工作分解、依赖、负责人和统一时间窗 |
| WorkOrder | 这一次具体要做什么 | 输入、SOP、交付物、DoD、风险、预算、期限、Owner 齐全 |
| SOPRun / StepRun | 每一步做到哪里 | 每步有产物、验证、证据、异常和实际执行人 |
| Deliverable | 这项工作交出了什么 | 模板必填项、质量检查、版本和审阅记录齐全 |
| Handoff | 下一个岗位是否真正接住 | 接收人明确、交接包完整、接收方验收 |
| Action | 对外系统发生了什么 | 通过既有审批与执行内核，有回执；未知不自动重试 |
| Metric / Observation | 结果如何度量 | 公式、分母、窗口、来源、主体去重、近似 / 核验状态明确 |
| Approval / Permission | 谁有权允许什么 | 人、范围、对象、版本、有效期和风险等级明确 |
| Learning / RuleChange | 下一轮具体改什么 | 旧版 → 新版、依据、影响范围、审批人和回滚方式明确 |

完整字段与状态机见 [03-data-and-product-spec.md](03-data-and-product-spec.md)。

## 5. 核心产品功能

### F01 业务上下文与目标工作台

- 导入 Askovo 结论或填写用户假设；
- 显示上下文缺口及其影响，不用一张“完成度分数”掩盖关键缺失；
- 把业务目标拆成结果指标、过程指标与护栏指标；
- 目标可关联多个 Workstream，但每个 WorkOrder 只设一个主责 Owner 和一个主要交付目的。

### F02 岗位能力目录

- 查看 18 能力域与 40 岗位族，而不是安装 40 个 Agent；
- 每个岗位显示使命、职责、输入、SOP、KPI、交付物、模板、上下游和人审点；
- 支持按企业类型、业务目标、自动化程度、风险和现有数据筛选；
- “适用”不等于“已验证有效”，能力上线状态与业务效果状态分开显示。

### F03 工作委托与工作分解

- 从模板或既有目标创建 WorkOrder；
- 检查输入、依赖、权限、预算、时间、交付物和接收方；
- 将跨岗位目标拆成有向依赖图，禁止无输入的并行空转；
- 每个任务有下一步、阻塞原因和预计人工时间；
- `mkt next` 未来应从“活动排期下一步”升级为“全业务工作下一步”。

### F04 专业 SOP 运行器

- 每步明确 Agent / 人 / 协作的责任；
- 支持条件分支、返工、暂停、升级和人工接管；
- 步骤完成必须附产物和 DoD 结果，不能只打勾；
- SOP 修改生成新版本；正在运行的实例继续绑定原版本，迁移需明确审批；
- 平台操作步骤只生成 Action Request，实际写入仍走既有统一写路径。

### F05 交付物工作室与方案模板

- 模板实例化、协作编辑、版本 diff、事实引用、权利与合规检查；
- 每类交付物有专属 QA Rubric，不只用通用“内容不错”评分；
- 审批分为业务正确性、品牌 / 法律、执行载荷三个独立维度；
- 交付物可关联后续动作、接收方和结果事件；
- 文件生成不等于验收通过，验收通过不等于业务有效。

### F06 跨岗位交接中心

- 标准交接：内容→社媒、达人→投放、活动→SDR、SDR→AE、AE→售前、成交→CS、客服→产品 / Askovo；
- 显示缺字段、未决承诺、责任人、SLA 和拒收原因；
- 接收方签收后才算交接完成；
- 拒收必须返回具体缺项，而不是“质量不行”。

### F07 授权执行与异常台

- 复用 plan / queue / approval / dry-run / pause / quota / suppression / ledger；
- 将执行审批绑定到 WorkOrder、Deliverable、SOP 版本、目标对象和账号；
- 对外发布、广告花费、合同承诺、报价折扣、危机回应等采用不同权限；
- 未知结果、平台限制、投诉、舆情、数据异常进入统一异常台；
- 禁止业务层直接调用 transport 或绕过现有写路径。

### F08 KPI、结果与经营复盘

- 指标字典先于看板；无公式、来源和窗口的指标不上线；
- 比率同时显示分子、分母与样本量，分母为零显示“不可计算”；
- 平台动作、任务推进、业务结果三层保持分离；
- 支持按 WorkOrder、角色、Workstream、主体和时间窗切片；
- 复盘必须落到规则变更：SOP、模板、指标口径、权限或下一轮工作分解；
- 描述性归因不冒充因果，实验结论保留样本和限制。

### F09 SOP / 模板 / 指标治理

- 版本、Owner、适用范围、评审、弃用、回滚和变更记录；
- 业务专家负责方法正确性，平台 Owner 负责平台规则，RevOps 负责指标口径；
- 从真实运行失败与拒收原因提出修订候选，不自动改生产 SOP；
- 每次改动可追踪受影响的工作、模板和审批。

## 6. 三条端到端业务流

### 6.1 内容到真实使用

```text
内容运营接收入口消息规范
→ 内容 brief 与事实包
→ 文案 / 创意交付物
→ 内容与权利验收
→ 社媒 / SEO 平台适配
→ 执行审批与发布
→ 评论、问题与有效互动跟进
→ 激活 / 持续使用事件核验
→ 内容 brief、平台 Overlay 与选题规则回流
```

“发布量”只进入过程层；内容的主结果可以是合格问题、目标任务完成或激活，具体由工作目标决定。

### 6.2 B2B 需求到续约

```text
Askovo 提供已确认 ICP / 价值主张
→ Demand Gen 建目标账户与培育计划
→ SDR 核验触发、角色、问题与接触资格
→ AE 接收并验收合格商机
→ 售前确认范围、技术成功标准与 POC 边界
→ AE 完成商务、合同与到账记录
→ CSM 接收承诺、成功计划和利益相关人
→ 采用、风险、续约 / 增购
→ 客户营销在取得授权后沉淀案例与推荐
```

任何阶段都不能用上一阶段动作替代本阶段证据。例如“开会”不等于合格商机，“POC 成功”不等于付款，“续约报价”不等于续约。

### 6.3 用户风险到服务恢复

```text
使用 / 服务 / 账单信号进入
→ 用户运营或 CSM 判断分群与风险
→ 客服先处理阻碍使用的问题
→ 成功计划、责任人和期限
→ 授权触达与内部协同
→ 用户确认问题解除
→ 续用 / 续约 / 复购独立观察
→ 高频问题回传内容、产品和 Askovo
```

触达完成不能关闭风险；必须由问题解除证据、用户确认或经定义的产品行为证明。

## 7. 人机分工与风险原则

| 风险级别 | 例子 | Agent 默认权限 | 人的责任 |
|---|---|---|---|
| R0 只读 | 读取授权数据、汇总、去重、生成待核对指标 | 可自动 | 保证数据来源和访问授权 |
| R1 内部草稿 | brief、文案、方案、SOP 草稿、内部任务 | 可自动，须可复核 | Owner 验收业务正确性 |
| R2 可逆内部写入 | 建任务、更新草稿状态、内部标签 | 在授权范围内执行 | 处理异常与冲突 |
| R3 对外或可追踪承诺 | 发布、触达、广告花费、客户交付、POC 范围 | 准备与 dry-run | 具名人审批版本、对象、账号、预算 |
| R4 高风险 / 难逆 | 合同、付款、法律声明、危机回应、隐私数据、重大折扣 | 不自主执行 | 有权限的业务 / 法务 / 财务负责人决定 |

所有级别都保留：最小权限、授权账号、暂停、审计、未知结果人工裁决和禁止绕过平台控制。

## 8. KPI 设计原则

1. **结果 KPI**：岗位真正要改变的结果，如合格 pipeline、激活、续约、净收入、开发者成功调用；
2. **过程 KPI**：交付周期、有效率、SLA、验收通过率，只用于管理执行；
3. **护栏 KPI**：退订、投诉、错误、退货、折扣、数据缺失、账号风险等，防止结果优化伤害业务；
4. 不使用一个综合“岗位分”掩盖 trade-off；
5. 目标值来自企业基线、历史同口径数据和本轮资源，不提供伪精确行业阈值；
6. 比率必须保存分子、分母、去重主体、资格条件和观察窗口；
7. 财务收入区分合同、订单、到账、净收入；产品使用区分注册、激活、持续使用；
8. 过程归因、财务记账和因果实验是三种不同语义，不合并成一个 ROI 数字。

## 9. 与现有实现的关系

| 新能力 | 复用 | 必须新增 / 改造 |
|---|---|---|
| 工作委托 | plan、campaign、scheduler | WorkOrder、依赖、Owner、交付物与状态机 |
| 专业 SOP | workflows、playbook_model | 业务 Step Contract、DoD、异常分支、版本运行 |
| 交付物 | value_artifact、value_delivery | 通用 Deliverable、模板、QA、业务验收和 Handoff |
| 执行 | approval、pipeline、action_runner、queue_runner | 业务对象与执行审批指纹关联，不新增绕过通道 |
| 对象与交接 | contacts、followups、conversion | Account / Opportunity / Customer 通用化；销售案例 Overlay 化 |
| 结果 | task_outcome、journey、result、experiments | Metric Dictionary、Observation、护栏和岗位视图 |
| 复盘 | retro、revise、operations_memory | SOP / 模板 / 权限规则变更审批与回滚 |
| 页面 / 入口 | CLI、MCP、Skill | 工作台的业务导航与统一 Read Model；CLI / MCP 不伪造自动执行 |

## 10. 明确不做

- 不做“输入产品名，一键替代整个市场部”；
- 不替 Askovo 宣布市场、ICP、定位或定价已验证；
- 不用同一套 SOP 强行覆盖 B2B SaaS、电商、直播、本地门店和开发者生态；
- 不默认全自动发布、花广告费、签合同、承诺 POC、处理危机或导出敏感数据；
- 不将平台注册、模板数量、SOP 文档数量当成业务效果；
- 不将发送、曝光、会议、POC、报价或合同中的任何一个单独冒充收入或客户价值；
- 不在没有客户授权时把交付记录改成公开案例；
- 不通过多账号、代理池或自动重试绕过平台限制。

## 11. 整体验收标准

这套设计只有满足以下条件，才算从“文档方案”变成“业务产品”：

1. 任选一个岗位族，都能创建有输入、有步骤、有交付物、有 KPI、有验收、有交接的 WorkOrder；
2. 07–46 每个岗位族都至少被一个可运行能力域覆盖，无“只在名单里出现”；
3. 新用户不读源码，也能从工作台知道“现在做什么、缺什么、谁审批、什么算完成”；
4. 一个跨岗位流程能在交接处拒收缺项，并追踪返工；
5. SOP 步骤没有产物和 DoD 证据时不能完成；
6. 所有对外写动作仍通过既有执行内核，测试证明无旁路；
7. 发送动作不会增加激活、续约、收入等业务计数；
8. 所有比率可展开公式、分子、分母、窗口和来源；
9. 行业 Overlay 不会把 FinOps 报价、固定销售阶段或消费电商指标强加给其他行业；
10. 至少三条灯塔流程完成真实 dogfood，并由业务接收方验收，而不只通过单元测试。

实施切片与详细测试见 [04-roadmap-and-acceptance.md](04-roadmap-and-acceptance.md)。
