# Growovo: implementation status

## Agent Native service frame (2026-11-26)

- **Managed Growth**: continuous market observation, qualified opportunities, authorized actions, relationship follow-up and operating reviews. This is the first flagship service to validate through reduced repetitive work.
- **First Users**: real demand discovery, first-use progression, onboarding help and activation evidence; goal-oriented, never a fixed-user guarantee.
- **Distribution Intelligence**: SEO/GEO checks, agent discovery and installation tests, first value and repeat measurement.
- The host agent chooses the operating path. Growovo preserves authorization, identity, quota, suppression, execution, readback, recovery and persistent business state. Sends are not conversion; execution, engagement, activation, retention and incremental growth remain separate.

## Guided execution strategy and preparation scheduling (working tree, 2026-11-26)

- `growth output-guide` turns a partial product draft into one question at a time, with purpose, example, suggested default, and structured JSON output. Answers persist without discarding existing fields.
- `growth output-plan` compiles `growovo.execution-strategy/1`: goal decomposition, platform/wave allocation, preparation TODOs, concrete targets/content, and measurement events. JSON and Markdown share the same contract. `output-lint --require-ready` rejects blueprint quotas without reviewed material.
- Preparation covers original titles/content/my-voice review, reply topic/KOC mining and reply-strategy review, and DM prospect mining/qualification/content review. Independent roots start before the first wave; missing branches advance with a per-tick bound.
- `preparation_runtime` persists attempts, supports controlled host-result recovery, freezes exact wave snapshots, and resumes later preparation after wave reconciliation. Strategy changes invalidate state; stale reviews and candidate counts do not become ready supply.
- Top-level scheduler strategy references propagate into wave approval. Strategy SHA-256 joins existing job, queue, item, account, and window binding. Short supply returns `supply_not_ready` without dispatch; legacy jobs without strategy are unchanged.
- Freezing rejects surplus and cross-wave duplicate reply/message targets as `supply_scope_invalid`. Recovery items use `replaces` plus original execution results to prove same-scope, one-to-one replacement with an untouched target; recoveries do not reduce original supply gaps. Scheduler recovery output distinguishes same-job retry/approval/reload/build diagnosis/reconciliation from the narrowly allowed new recovery job.
- Scheduler preparation output is a bounded summary rather than repeated full content/state/attempt payloads. `jobs-serve` continues when a short-supply tick made preparation progress; full evidence remains on disk.
- `growovo.business-progress/1` persists business-readable scope, preparation, evidence and recovery events with fact/impact/next action/counts/evidence/technical fields. `cycle progress` provides filtered Chinese and JSON views; consecutive duplicates are suppressed, dry-run writes none, and logging failures never rewrite execution receipts or imply growth. Deferred probes and channel blockers are translated into business facts and next actions.
- Queue IDs use `campaign:item` with `strategy_item_id` preserved for approval/reconciliation. Zero quotas are normalized, and misplaced `content_rules` fail before approval.
- `growovo.execution-quality/1` scores audience/content quality and assigns communication hooks. `growovo.outcome-funnel/1` separates actions, qualified interactions, first runs, accepted results and second use with per-100-action rates. `growovo.experiment-allocation/1` reserves high-quality exploration while scaling evidence-backed variants instead of averaging products. Unknown outcomes remain unknown.
- Scheduled waves now use the approved source fingerprint as their only source gate; unsigned execution still uses the daily baseline. This removes the same-day conflict between a valid approved build and a stale morning baseline while keeping real post-approval source changes blocked. Regression coverage includes both stale-baseline acceptance and approved-source mismatch rejection.
- Same-platform cadence caps at two consecutive actions; the scheduler then inserts another channel or waits `rotation_gap_sec` (120 s). GitHub replies use a 45 s minimum gap, X replies stay at 90 s, and the trailing streak is restored from the ledger at wave start. GitHub 403 first checks the target issue: locked or closed targets are isolated and the channel continues; open or unknown targets stop the channel conservatively. Regression coverage includes locked-issue isolation, open-issue channel stop, cross-wave streak recovery, and mixed-platform interleaving.
- Scheduler recovery now treats preflight and lock contention as retryable conditions: preflight tries every live tab until it finds a logged-in identity instead of failing on the first login page, `jobs-serve` waits out `scheduler_already_running` instead of exiting, and due jobs blocked by transient preflight/login issues keep polling instead of returning `no_runnable_jobs`. Regression coverage includes logged-in tab selection and both serve recovery cases.
- Discord readback now scrolls to the bottom of the message list and uses text presence as a fallback when a virtualized list has not mounted the new row yet, so a real post is not misclassified as indeterminate and does not stop the whole channel. The author lookup also walks back to the nearest group header because Discord omits the username on continuation rows; without that, a grouped message was read as anonymous and the channel stopped.
- Night supply generation is isolated per run id with unique item ids and no post-approval queue mutation; parallel GitHub issue-state checks reduced 480-item generation from about 8 minutes to about 35 seconds in the current workspace.
- `growovo.strategy-decision/1` turns 20 mechanism cards plus the 606-record experience corpus into contextual strategy selection and adjustment. Cards retain corpus examples and usage boundaries; decisions expose reasons and missing inputs. Accepted results enable compound distribution, second use supports scaling, and channel stops, low quality, missing first value or no interaction take different paths instead of one fixed strategy.
- **Verification:** 2809 tests, `mkt demo`, and `git diff --check` pass with no real account sends. `examples/execution-strategy-300.json` closes at ten waves and 300 configured actions, while its unmaterialized supply remains an explicit gap. External miners, content generators, my-voice reviewers, X DM writes, production workers, and business growth still require independent real acceptance.

## Scheduled batch stability hardening (working tree, 2026-11-26)

- Signed `policy_overrides` bind exact execution windows, channel cadence, content rules, queue freshness and inbox actor limits to the approved job. The same overrides drive preview and execution. Unknown fields and safety-stop/quota layers cannot be overridden through this route. Six X originals with source links have an end-to-end offline regression outside the daily window.
- `cycle jobs-serve` waits for, executes and settles jobs without a chat agent; `--once` supports external schedulers. Its operations block separates scheduler token usage (zero), unmeasured upstream model work and elapsed time. Job cards retain engine state, scheduler state, exit code and token measurement separately from business outcomes.
- Browser claims persist `dispatching` and adapter `acknowledged` phases. Receipt reads share the existing account/channel lease with writes and return `browser_write_in_progress` instead of navigating a busy route. The acknowledgement phase alone never proves a platform write.
- Job transitions enter a persistent notification outbox before scheduler state is saved. `cycle notifications` lists undelivered events; injected delivery adapters need a receipt, and failed deliveries remain pending. No external notification channel is implied.
- Scheduled GitHub supply checks the actual `gh` executable before approval. Existing scoped queues, immutable workers, hourly slots, partial-completion and stopped-job settlement regressions remain in force.
- **Current verification:** 2677 offline tests and `mkt demo` pass on the combined business-evidence and scheduled-runtime candidate. The installed wheel exposes task-result, jobs-serve and notification commands; empty notification receipts stay failed and pending. No production worker, external notification channel or business growth is claimed.
- Pages re-run removes stale `github-pages` artifacts only from the current `run_id` before upload, preventing duplicate-artifact deployment refusal without deleting other runs or releases. This workflow fix still requires GitHub Actions verification after merge.

## Execution evidence and current relationship state (working tree, 2026-11-26)

- `grow status --explain` adds a read-only `ovo.task-result/1` projection alongside C-01. It separates running, external waits, user decisions, partial results, completion and inability to complete, retains executable recovery commands, and scopes missing product events to activation/retention instead of failing the whole operations task. CLI and MCP use the same `explain_status` implementation.
- Verified channel completion must match a committed ledger record for the same service, action, attempt, account, target, channel, claim and readback. The unified gateway stamps that identity onto each ledger append. Independent reconciliation restores the frozen attempt payload instead of accepting a replacement target/text, then persists its unique external readback. Observed/independently verified metrics need `growovo.metric-evidence/1`: matching metric/account/window, named collector and version, raw observations, definition hash and a recomputed value; file existence and SHA-256 alone are insufficient.
- Cycle execution claims the action before reserving grant quota under the same file lock used by grant/revoke/consume/settle. Each attempt has an idempotent reservation: definite no-execution releases it, completed or externally unknown outcomes retain it, and duplicate claims consume nothing. Function return no longer becomes generic `executed`; completed, waiting verification, manual handoff, preview and blocked stay distinct.
- Lifecycle retains historical furthest stage separately from current relationship state (`follow_up_due`, `active`, `engaged`, `silent`, `churn_risk`, `churned`, `reactivated`, `do_not_contact`) with explicit risk/churn windows.
- Agent adoption now distinguishes `PROCESS_PASS`, `AGENT_SESSION_PASS`, `FIRST_VALUE_ACCEPTED`, `EXTERNAL_ADOPTION` and `RETAINED`; process checks and human declarations cannot skip fresh-session or external-result evidence.

## Lifecycle projection and shared experiment export (working tree, 2026-11-25)

- `growth feedback-export` projects named human classifications and exact source quotes into `growovo.product-feedback/1`. It binds existing conversations, deduplicates stable feedback IDs, rejects conflicting duplicates and writes only new output. Source state, canonical evidence and product decisions remain unchanged. CLI, Skill and MCP share the projection.

- `growth opportunity-import` requires timezone-aware `observed_at` and computes a bounded validity window from `valid_until` or `freshness_hours`. Expired records remain visible but cannot enter `next_action` or lifecycle follow-up queues; legacy unknown-freshness records are not treated as current. The projection is read-only and does not rewrite stored opportunity history.

- `growth cycle wake` and `operator-serve --host-adapter` invoke an authorized local host adapter for open cycles and persist its proposal through the existing risk policy. Invalid output leaves the cycle open. Proposal execution is off by default and requires explicit `execute_accepted_by`; accepted actions still use the original execution gates. Optional `feedback_enabled` creates bounded parent/child feedback cycles with a maximum depth and no duplicate follow-ups.
- `geo agent-adoption run` executes discover/install/first_success as fresh operator-authorized host processes with deterministic output/file checks and inspectable evidence. Results distinguish `PROCESS_PASS`, `AGENT_SESSION_PASS`, `FIRST_VALUE_ACCEPTED`, `EXTERNAL_ADOPTION` and `RETAINED`; fresh-session, external-user and retention evidence cannot be skipped by real input labels or named acceptance alone.
- `growth lifecycle` projects existing opportunities, conversations and experiment events into source-prefixed subjects. Historical furthest stage stays separate from current relationship state and explicit risk/churn windows. Cross-source identity maps, verified activation/retention/payment, prior activation and shared DNC/bounced suppression remain mandatory; unqualified events stay visible.
- `growth experiment-export` emits the shared `ovo.experiment-contract/1` with explicit event bindings and no automatic causal credit.
- `growth efficiency` combines explicit per-channel human-time/cost evidence with observed conversations and verified activation events carrying an explicit channel. It reports minutes/cost per interaction and activation, null zero denominators, unqualified and unassigned events, no cross-currency sum and no causal/ROI claim. CLI, Skill and MCP share the projection.
- `growth cycle resolution` projects refused, blocked, expired or result-unknown cycles into `ovo.problem-resolution/1`. Missing grants become incremental permission requests; unknown external effects require reconciliation before retry. The read-only projection executes nothing and can be independently evaluated by `python3 -m ovo_acceptance resolution FILE`.
- `growth report` projects cycle creation by `created_at` and execution/results by `executed_at` into separate half-open-window counts, so cross-midnight work is not backdated. Legacy executions without a timestamp remain `undated_records`. It also projects current lifecycle observations and named user-decision queues. Current lifecycle contacts are never presented as new in-window conversions or causal growth. The projection is read-only and fails on any damaged cycle JSON rather than silently omitting it. CLI, Skill and MCP (`mkt_growth` action `report`, JSON only) share the same projection.
- Verification: lifecycle, engagement, experiment and CLI tests pass; projection performs no external send or business-outcome upgrade.

## R3 P0 hardening (2026-11-24)

- A channel action can no longer be marked `completed` without a completion type. `verified` requires a receipt with `action_id`, `channel`, `sent_at`, `idempotency_key` and `readback`; `attested_manual` requires a named operator and a reason. `declared` completions are rejected. Metrics report `completed_verified` / `completed_attested` / `completed_declared`, and downstream actions are marked `dependency_quality: attested` when they rest on a manual attestation.
- `growth evaluate` now carries provenance per metric (`owner_declared` < `observed` < `independently_verified`, plus window and definition hash). `primary_success` answers "did the number reach the target"; `primary_verified` answers "was it measured on the same basis". Bare numbers stay `owner_declared` and can never produce `primary_verified`.
- Execution leases carry a monotonic fence kept in `execution_fence_counters`. The heartbeat marks its `LeaseState` lost when renewal is refused, and `run_action` re-checks the lease at entry and again right before dispatch. A lost lease returns `lease_lost` with `retryable: false` and the dispatch never happens.
- **Verification:** 2476 offline tests pass, including the new `tests/test_execution_lease.py` (6 cases), completion-type, provenance, mixed-source and legacy-completion tests; `mkt demo` still passes.

## Final release review hardening (v0.21.0, 2026-11-24)

## Canonical run outcome (2026-11-24)

- `core/cycle_report.py` now emits `task_outcome` alongside the legacy fields: `outcome` is `resolved` / `partial` / `unresolved` / `unknown`, with `basis` (`target`/`planned`/`none`), `target`, `planned`, `attempted`, `committed`, and machine-readable `reasons` (`wave_failed`, `wave_partial`, `deferred`, `unattempted`, `engine_error`).
- This is the field a CLI, MCP surface or night report should read when the question is "did the run resolve the task?". Legacy `report.status` (`complete`/`attention`) and `wave.status` (`complete`/`partial`/`failed`) remain for compatibility but answer different questions and must not be used as the business outcome.
- A failed wave with committed work is `partial`; a failed wave with no committed work is `unresolved`; zero target and zero plan is `unknown`, never success.

## Unified runtime optimization, 2026-11-24

- **Business-first execution policy:** AUTO/GATED now depends on write primitives, queue support and technical verification only. X, Discord and Email are AUTO; platform rules and compliance codes are non-blocking risk warnings and cannot force human-assisted compilation. Account authorization, identity, pause, DNC, quotas, readback, CAPTCHA/risk stops and unknown-result reconciliation remain independent execution-safety boundaries. LinkedIn no longer requires `MKT_LINKEDIN_AUTO` or terminal confirmation.
- **Normalized storage and bounded I/O:** conversations and messages have separate SQLite identities; JSON is a read-through compatibility projection, not a synchronous write inside online transactions. Schema initialization is locked and uses WAL; GitHub/Gmail independent reads use at most four workers. Experiment advice enumerates authoritative SQLite state and still migrates legacy JSON.
- **One ready path and account lanes:** legacy waves run through `growth operator-serve --wave`; local eligibility is computed before browser work. Explicit wave collection skips the browser when no action is executable, while configured standing observation still reports DMs with zero sends. `action_gateway` is the single lease/authorization entry for CLI action, MCP, queue, cycle, workflow replay and growth execution; channel CLI shortcuts that still call their original channel functions also take the same account/route lease. SQLite execution leases serialize each account/route without stopping reads.
- **One X browser route:** `mkt x publish/reply`, `mkt action`, MCP and workflow replay default to `browser-attach` (WebBridge managed tab) unless the caller explicitly asks for the legacy route. Routine X writes no longer fall back to vendor CDP either: `routine` is converted to the owner-attested route and fails with `authorization_missing` when no owner-attested policy exists. Identity observation and execution happen in the same tab. Vendor CDP (9222/`--cdp-url`) is explicit `--legacy-cdp`; `mkt x publish/reply` now goes through `action_gateway`, and `mkt x message/engage` (browser-attach does not yet implement DM/follow/like) requires explicit `--legacy-cdp`. X read paths (search, tweet text, post metrics, readback URL, account enrichment) also default to WebBridge; `cdp.connect` for X requires `MKT_X_LEGACY_CDP=1`.
- **Official API acceptance support:** GitHub App Issue creation joins the same approval/Gate/quota/pipeline path as replies. Gmail accepts local OAuth file paths, prefers refresh over stale file access tokens, and supports a new self-addressed thread using the returned threadId. Both use independent readback.

## External validation still required

- Full platform deep-research DoD is not complete. Registry size and document count cannot substitute for current official rules, practitioner methods, failure cases and platform-specific execution validation.
- Real account, proxy and authorized live-write tests are outside CI. They require separate authorization, platform/action/transport checks and readback evidence.
- Signal interpretation, opportunity and journey modules are deterministic reasoning aids, not proof that host semantics are true, demand exists, growth is causal, or revenue will follow.
- Local value-chain fixtures prove the state machine and real subprocess accounting only. External delivery receipts, user completion and production reliability still need authorized real-world verification.
- Experience counts and freshness are build-time facts and must be regenerated with the pipeline and status page. Previous counts such as 108/117 were snapshots, not permanent facts.
- Synthetic demos and local fixtures do not prove external business results, paid demand, production reliability or exact-once delivery.
