# 案例：Askovo —— Growovo 的首位 dogfood 客户（P0，进行中）

> **角色**：Growovo 以操作员身份接管 Askovo 的 GTM，用一次真实投放验证「operator 分钟 / human 分钟」账本与四阶段纪律。
> **周期**：2026-10-31 启动 · D14 门禁 = 2026-11-14 · 数据截至 2026-11-02
> **[English version](askovo.en.md)**

## 背景与目标

[Askovo](https://github.com/roy-tong/askovo) 是 ovo 家族的「判断层」：SURE 证据引擎，把产品与业务推理落在可核验的证据链上。它与 Growovo 的关系是上下游——Askovo 回答「该做什么」，Growovo 回答「用户从哪来」。

本次案例把 Askovo 作为 Growovo 的 **P0 dogfood 客户**：不开新能力、不写演示数据，端到端跑一遍 GTM 四阶段，并预先注册门禁：

| 门禁 | 判据 |
|---|---|
| **P0 过** | ≥1 个真实价值事件，且全流程人工 ≤12 小时 |
| **Kill** | 人工 >20 小时，或零注册 → 退回 RaaS 服务形态 |

「价值事件」的口径在启动当日就写死：因 Askovo 尚未发 PyPI，量测改用 GitHub 流量近似，**近似口径已在台账中标注**，不冒充精确数。

## 台账（本案例的核心产出）

全流程记两层分钟数：operator（agent 操作时间）/ human（人必须亲手做的时间）。

| 截至 | operator | human | 预算余量 |
|---|---|---|---|
| 2026-10-31 | 275 分钟 | **5 分钟** | 62%（预算 720 分钟人工） |

人的 5 分钟花在哪里：审阅定位文档。其余全部动作——体检、误报修复、5 件资产、安装路径验证、65 个未提交文件的测试与提交（119 测试全绿后才动，[5f2e338](https://github.com/roy-tong/askovo/commit/5f2e338)）、README 改写、博客发布、渠道上线验证——都是 operator 分钟。

一个插曲：Askovo 未发 PyPI 且无上传凭据，安装路径当日下午改道 `pipx install git+https://…` 并在干净 venv 实测通过——阻塞不等人，先找已验证的替代路径，把「等待凭据」从关键路径上拿掉。
