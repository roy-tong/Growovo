# GitHub

> 一句话：开发者找工具的第一站，也是唯一"给东西就能换回东西"的地方 · 研究日期 2026-11-03
> 官方口径：**部分已核**（API 限额已核；spam 政策页抓取失败，标 [待核]，见 `docs/risk/github.md`）
> 自家实测：**有，而且是最强的一条**（Verovo 交付链：12 次触达 → 3 个硬产物，2026-09）

---

## 1. 这里是什么地方

**谁在这里**：所有写代码的人——从大厂工程师到一个人写周末项目的独立开发者。这里是他们找工具、看别人怎么写、报 bug 的地方。

**他们来干什么**：
- 搜"有没有现成的轮子"，而不是刷信息流
- 读 README 决定要不要试
- 在使用中遇到问题，开 issue 问
- 给觉得自己能改的地方提 PR

**它在这门生意里的角色**：**唯一的"转化层"**。别的平台带来的是注意力和讨论；GitHub 带来的是 star、fork、issue、PR——都是能留下来、能被搜索到、能证明"有人在用"的东西。

**核心机制（这条最重要）**：GitHub 的交流货币是**代码、复现、fixture、具体发现**。
你在 X 上给人注意力，在邮件里给人时间，在 GitHub 上给人**能直接用的东西**。你的产出如果是技术成果，在对方语境里就是硬通货；如果你只能给"我们产品很棒"，这里一分钱都不值。

---

## 2. 内容怎么被看见

| 路径 | 怎么工作 | 特点 |
|---|---|---|
| **搜索** | 仓库名、README 关键词、topic 标签 | 长期有效，是最稳定的一条，但要有人真的搜那个词 |
| **trending** | 新仓库短期 star 增速 | 一次性，且需要"爆发"，靠日常积累撬不动 |
| **awesome list** | 别人维护的清单，收录你的项目 | 长期稳定流量，但要对方愿意收 |
| **上游项目的 issue/PR** | 你在他人的仓库里留下有价值的痕迹，看的人顺着名字点过来 | **转化最高**，因为看到的人是带着具体问题来的 |
| **README 本身** | 有人点进来，前三屏决定走不走 | 决定"来了之后留不留" |

**新项目有多难**：0 star 的项目几乎不会被自然搜到。所以早期不要指望搜索，要靠**上游交付链**（去别人的仓库留下东西）。

## 3. 官方规矩

**已核的部分**：

| 项 | 数值 | 来源 |
|---|---|---|
| API 限额（匿名） | 60 次/小时 | 官方文档，代码 `throttle.OFFICIAL_LIMITS` 同步 |
| API 限额（带 token） | 5,000 次/小时 | 同上 |

**结论**：走官方 API，token 顶格，**没有任何需要绕的场景**。频控的真实约束不是限额，是"内容有没有价值"。

**待核的部分** [待核]：GitHub 的 Acceptable Use / spam 政策原文（站点抓取失败，需人工核一遍）。已知的边界是：禁止 issue/PR 滥用、买星卖星、不真实互动。

**违规后果**：仓库被限制、账号被冻结、组织被标记。最重的是账号冻结——所有仓库、issue、PR 全部不可用。

## 4. 真实打法

### 主线：上游交付链（唯一被自家数据证明有效的打法）

**做法**：找那些"正在被你的技能解决的问题困扰"的开源项目 → 读他们的 issue → 自己复现问题 → 提一个有真实发现、有最小复现的 issue 或 PR。

**自家实测数据**（Verovo，2026-09，12 次触达）：

| 动作 | 结果 |
|---|---|
| 12 个 issue/PR | 4 条有人回应（约 33%） |
| 其中 1 个 PR | 被上游合并（OpenLIT #1476），代码真的进了对方仓库 |
| 1 次 conformance vectors 提交 | 对方发现我们自己的 3 个真缺陷 → 变成我们的回归测试 |
| 1 次 CI 集成 PR | 外部仓库主动集成 |

**三个月里能说清来源的 star，全部来自这条路。** 不是发帖带来的。

**为什么有效**（四个机制，值得记住）：
1. **货币匹配**：你的产出本来就是代码和发现，这是这里的通用货币
2. **上下文完整**：issue 自带代码、版本、CI，讨论落在可验证的事实上，不需要你"证明自己"
3. **公开声誉**：帮别人修 bug 是有观众的行为，维护者愿意回，因为对他也有好处
4. **工作语境**：维护者是在工作时间按自己节奏处理 issue，不是在刷手机消遣

**做对的样子**：
```
标题：<组件> double-counts tokens when retry succeeds on second attempt
正文：
- 版本：x.y.z
- 最小复现（10 行以内）
- 实际结果 / 期望结果
- 影响范围：什么样的使用场景会踩到
- 我试过的绕过方案（如果有）
```
**不要**：先说"我们做了个工具可以帮你"，再说问题。

### 副线：README 钩子

README 前三屏决定别人留不留：一句话说清"这是什么问题" → 一行安装 → 一个 30 秒能跑通的例子 → 为什么信你（测试数、案例、边界）。

**自家教训**：Verovo 曾经从 HN 引流，但 README 里没有任何指向审计报告的出处，访问者从 HN 进来后找不到进一步的材料——后来专门补了"审计出处"一节。

### 副线：Discussions

适合承接"不是 bug 但需要讨论"的问题（用法、方案选择）。开起来之后是低成本的内容沉淀，但需要有人回，否则很快就荒。

## 5. 死路

| 做法 | 为什么没用 |
|---|---|
| **买星** | 自家最惨的一次：92+42+约 13 颗，全部污染归因。fork 率 3.7% 当场暴露异常（正常 5–20），任何人做体检都能看出来 |
| 模板化 issue | 维护者一眼认出，直接关，还可能举报。12 个模板 issue 的转化是 0 |
| 没有实质内容的 PR | 改个错别字、调格式，会被当成刷贡献 |
| star 互换群 | 同上，且会被平台批量清理 |
| 在 issue 里推销产品 | 这是最招人烦的做法，而且会连累账号 |
| 建一堆仓库充数 | 搜索权重分散，反而拖累主仓库 |

**一条判断标准**：这个动作，如果我是一个陌生人，会希望别人对我做吗？不会，就别做。

## 6. 这里的人怎么说话（人味）

**语气**：技术性、克制、就事论事。维护者每天看几十个 issue，**你只有三行字的机会**。

**被尊重的表达**：
- 先给复现，再给判断："在 x.y.z 上，这样调用会抛异常（附代码）"
- 说清楚你试过什么："我试过 A 和 B，都不行，所以我怀疑是 C"
- 承认是自己用错了："是我配置错了，不是 bug，抱歉打扰"（这种回复反而会让人记住你）
- 给最小复现，不要甩一整个项目

**一眼看出是"推广"的信号**：
- 开头是自我介绍或公司介绍
- 正文里突然出现产品链接
- 通篇没有一个具体版本号或代码
- 问题描述模糊到可以用在任何项目上（"希望支持更多场景"）
- 结尾"欢迎交流/合作"

**好的开头**（真实风格）：
> "On v2.4.1, `retry=true` with a timeout causes the token counter to increment twice. Minimal repro below (12 lines)."

> "I might be misreading the docs, but `--strict` seems to skip validation for nested arrays. Here's what I expected vs what I got."

**忌讳**：
- 用"您好，我是XX公司的..."开头
- 在 issue 里谈商务
- 催维护者（"能不能尽快回复"）
- 一稿多投（同一个 issue 贴到十个仓库，这算 spam）

---

## 7. 账号与节奏

- **账号**：用真实身份（真人头像、真实名字或稳定 handle）。不要新建"产品官方号"去提 issue——用个人身份更可信。
- **频率**：**宁缺毋滥**。单仓库每天不超过 3 次互动是上限，实际上一个仓库一周一次都算多。
- **没有"最佳时段"**。维护者按自己的节奏处理，早上提和晚上提差别不大。
- **账号资产**：历史 PR、被合并的记录、star 过的仓库。这些是别人判断你"是不是认真的"的依据。

## 8. 风控与踩线

| 手段 | 性质 | 说明 |
|---|---|---|
| API 速率限制 | 已知 | 超限返回 403，窗口重置 |
| 滥用模式检测 | 已知存在，细节未知 | 短时大量 issue/PR、跨仓库模板内容、低质量提交会被标记 |
| 垃圾账号分类器 | 已知 | 农场号、异常关注图谱会被批量冻结（买星事故中可见） |
| 维护者举报 | 已知 | 推销式 issue/PR 是最常被举报的对象 |

**踩线信号**：issue 被无视且被关闭；账号突然无法评论；star 增长但 fork 不动（异常）。

**被处理了怎么办**：走官方 support 申诉。**账号冻结影响最大**，因为交付链的全部资产都在这个账号上——所以最高纪律是：**只做有真实价值的提交，永远不批量**。

## 9. 怎么衡量有用

**能拿到**：star、fork、issue 数、traffic（需要 token，且只有你自己能看）、PR 合并数、外部贡献者数。

**拿不到**：有多少人 clone 了没 star、有多少人读了 README 就走了。

**"被问到"长什么样**：
- 有人开 issue 问具体用法
- 有人提 PR 修你的 bug（最强的信号）
- 有人在别的仓库的 issue 里提到你的项目
- 有人问 license / 能不能商用

**常见误读**：
- **star ≠ 用户**。star 是收藏夹，很多人 star 完再也没打开过
- **fork ≠ 采用**。fork 可能只是"想看看源码"
- **traffic 的 clone 数会虚高**，CI 和爬虫都算在里面
- **买来的 star 会在两处露馅**：fork/star 比例异常、增长曲线不自然

## 10. 适不适合

**适合**：
- 开发者工具、库、CLI、SDK
- 任何"用起来比说起来更清楚"的技术产品
- 有真实技术积累、能持续产出发现的团队

**不适合**：
- 消费类产品（这里的人不会为了买日用品来 GitHub）
- 没有技术门槛的产品（无法参与上游对话）
- 想快速起量的产品（这条路是周/月为单位，不是天）

**搭配使用**：HN 或 Product Hunt 做一次性曝光 → 访问落到 GitHub → 用上游交付链把访问变成 star 和 issue → 用 dev.to 长文承接搜索流量。**GitHub 是唯一值得长期投入的那一个。**
