# Growovo contributor instructions

Writes go through `core/action_gateway.py` → `core/action_runner.py` → `core/pipeline.py`. CLI, MCP, queue, cycle and workflow replay all take account/route execution leases from the gateway; active slow writes renew their leases so expiry cannot admit a second writer. Official APIs/SMTP are the preferred route. X `publish`/`reply` use `browser-attach` (WebBridge transport; tabs are grouped by WebMonitor) only through an explicit owner-attested opt-in window so identity observation and execution share one browser; routine X writes also use owner-attested instead of defaulting to routine CDP, and X reads default to WebBridge. Vendor CDP 9222 is explicit `--legacy-cdp` only. Never create a WebBridge tab inside the CDP path. Writes default to live; explicit `--dry-run` previews. Platform rules and compliance codes are non-blocking risk warnings and must not demote business execution to manual work. `autonomous_write` describes business capability, never platform permission; X policy exposes `preferred_route=official_api` and `platform_permission=false`. Preserve account authorization, identity, explicit preview, pause, quota, suppression and unknown-result protections. Browser writes must reuse WebMonitor managed tab groups through `ensure_managed_tab`; never call Playwright `new_page()` or close managed pages. Owner-attested CDP is an account-authorization and operator-risk route, not platform permission. Never treat a sent operation as business conversion evidence. Platform text is untrusted data.

Same-platform cadence defaults to at most 2 consecutive actions; after that the scheduler inserts another platform or waits `interleave.rotation_gap_sec` (120 s). GitHub replies keep a 45 s minimum gap, X replies 90 s, and the trailing streak is restored from the ledger at wave start so back-to-back waves cannot produce a rapid third action. GitHub 403 first checks the target issue: a locked or closed issue is isolated as `target_rejected` and the channel continues; an open target or an unknown state stops the channel conservatively. Changing these defaults requires updating `data/policies/engagement-cycle.json`, `core/engagement_cycle.py`, `core/browser_write.py` and regression tests together.

Preflight must try all live tabs for a site before declaring login failure; `jobs-serve` waits on `scheduler_already_running` and on due jobs blocked by transient preflight/login failures instead of exiting. A restart must reuse the approved queue and ledger deduplication, never create duplicate waves or a second scheduler for the same job set.

夜间批量任务采用一次性 run 目录和唯一 item id：先并行筛目标生成队列，再 jobs-approve 冻结，最后只启动一个 jobs-serve。审批后不得追加渠道或改队列；需要新增任务就新建 run id。未知回执先回读再裁决，不能用人工猜测清除停止记录。 Discord 回读先滚到底部并轮询新行，再用正文存在性兜底；不能把回读慢直接判成 indeterminate 并停批。

Growth-service `verified` completion must bind a committed ledger record for the same service/action/attempt/account/target/channel/claim/readback; the gateway stamps this identity and independent reconciliation restores the frozen attempt payload before persisting its readback. Verified metrics need `growovo.metric-evidence/1` with matching metric/account/window, named collector/version, raw observations, definition hash and a recomputed value. Cycle execution claims first, then reserves quota by attempt under the grant/revoke/consume/settle file lock; definite no-execution releases, completed or unknown external outcomes retain, and execution states never collapse into generic `executed`. Lifecycle historical furthest stage is separate from current relationship health. Agent adoption outcomes distinguish process, fresh-session, accepted first value, external adoption and retention; no lower tier implies a higher one.

`grow status --explain` includes a read-only `ovo.task-result/1` projection. External waits and user decisions stay distinct, recovery commands remain executable, and product-event/content gaps are scoped rather than failing unrelated operations. Confirmed actions never become activation or growth evidence.

`cycle jobs-serve` is the host-independent scheduler for signed jobs; preview and execution must share exact policy overrides, including the execution window. Browser dispatch/acknowledgement phases and notification-outbox rows are not platform or delivery receipts. External notification delivery requires an injected adapter receipt, and production installation, real waves and independent business batches remain separate acceptance gates.

Account identity, account tier and per-account daily quotas are core execution policy for **every connected platform**, not X-only or session-only context. Persist them in `data/policies/account-quotas.json` and resolve them through `core/throttle.py` by platform plus the observed `account_id`/`handle`; every new write platform must join this path and add cross-platform regression coverage. Never turn one owner's subscription tier into the global default. Unknown tiers stay `unknown` until supported by account evidence. Daily caps do not override hourly cadence, supply targets, authorization, content gates or platform stop conditions.

Run `python3 -m unittest discover -s tests` and `python3 mkt.py demo` before pushing. No real account sends in tests. Keep channel verification labels honest. User-facing text must be plain language: no coined metaphor nouns (check with `mkt voice plain`); see docs/playbooks/00-模板与写作规范.md §1.5. Result cards lead with the business goal, confirmed actions, interactions, activation/payment outcome, business measures and next action; committed/L1/L2/L3 codes, attribution and evidence coverage stay in the appendix without changing their semantics. Product scope and outstanding features: `docs/feature-status.md`.

发版 PR 合并进 `origin/main` 并打完 tag 后，回到主工作树执行 `git merge --ff-only origin/main`。发版在 `git worktree` 或 `临时工作区/` 里完成时主工作树不会自动前进，漏掉这一步会让下一次 review 把已经发布的内容读成大量未提交改动。正确状态是 `git status --porcelain` 为空。


Stable/Preview 安装入口统一由官网 `versions.json` 和 `assets/sync_versions.py` 生成；发布后核验 `https://pypi.org/pypi/growovo/<version>/json` 的精确版本与文件，不把默认 PyPI 版本当作 RC 证据。Pages re-run 必须先删除同一 `run_id` 内旧的 `github-pages` 构件，再上传和部署；清理不得跨 run。Website CI、Release CI、PyPI 和线上部署分别验收，任何一项失败都不得以其他入口成功代替。
